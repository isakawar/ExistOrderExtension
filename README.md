# Order Smoke Test — QA Chrome Extension

Внутрішній інструмент для швидкого smoke-тестування створення замовлень на UA/PL
платформах після оновлення кодової бази 1С. Замінює ручний запуск JS-скрипта в
DevTools Console на UI з чекбоксами, live-логом і summary.

## Статус

- ✅ **UA** — повністю реалізовано (Phase 1–2).
- ⏳ **PL** — ще не реалізовано (Phase 3), у попапі показується як "не реалізовано".

## Встановлення (unpacked)

1. `chrome://extensions`
2. Увімкнути **Developer mode** (правий верхній кут).
3. **Load unpacked** → вибрати папку `ExistChromeEstension`.
4. Іконку розширення можна закріпити на панелі.

## Як користуватись

1. Відкрити сайт (UA) у вкладці Chrome.
2. Авторизуватись своїм звичайним QA-акаунтом.
3. Відкрити popup розширення — вгорі одразу видно **🟢 Connected: <hostname>**;
   платформа автоматично проставляється за поточним сайтом.
4. Перевірити/змінити телефон, кількість замовлень, доставку/оплату — над кнопкою
   запуску показується компактний прев'ю: скільки валідних комбінацій і скільки
   замовлень буде створено.
5. **Запустити Smoke Test** → підтвердити у діалозі (номер замовлень, платформа,
   сайт — все ще раз показано перед стартом).
6. Popup перемикається в компактний **Running**-режим: прогрес-бар, поточне
   замовлення, список уже виконаних з іконками статусів. Технічний лог згорнутий
   за замовчуванням ("Показати технічний лог").
7. За потреби — **Stop**: тест зупиняється між замовленнями, вже запущений запит
   не переривається, решта не запускається.
8. Після завершення — компактний **Completed/Stopped** заголовок (Passed/Failed/
   Skipped, тривалість), детальний список результатів (для помилок — розкривний
   **Details** з сирою відповіддю API), кнопки **Copy Summary** та **🔄 New Test**.

Розширення **не має власної авторизації** — воно виконує запити прямо у вкладці
сайту (через `chrome.scripting.executeScript`), тому використовується поточна
сесія/cookies браузера. Логін, пароль, cookies чи токени ніде не зберігаються.

### Reconnect після закриття popup

Chrome знищує DOM попапу щоразу, коли він втрачає фокус — але сам тест виконується
у вкладці сайту (`core/smoke-runner.js`, injected), незалежно від popup. Якщо
закрити/відкрити popup під час прогону, він виявляє активний тест (`self.__smokeRunning`
у вкладці) і підключається до нього замість того, щоб дозволити запустити другий
паралельний тест — прогрес, зібраний тестом до цього моменту, відновлюється.

### Пам'ять налаштувань

`chrome.storage.local` зберігає платформу, телефон, кількість замовлень і вибрані
delivery/payment (ключ `smokeSettings`) — щоб QA не вводив усе заново щоразу.
**Не зберігаються**: пароль, cookies, CSRF/access токени — розширення їх узагалі
не читає й не має до них потреби, тому й зберігати нічого.

## Архітектура

```
manifest.json
popup/
  popup.html / popup.css / popup.js   — UI, стейт-машина (INITIAL/RUNNING/COMPLETED), оркестрація запуску
core/
  site-config.js          — hostname → platform mapping (popup-only, detect/mismatch UI)
  scenario-generator.js   — генерація delivery x payment сценаріїв (platform-agnostic, injected)
  smoke-runner.js         — послідовний запуск сценаріїв, live-повідомлення (injected у вкладку)
  logger.js               — форматування Copy Summary тексту (лише popup)
platforms/
  ua/
    ua-config.js             — delivery/payment методи, бізнес-правила, константи (city/office id)
    ua-products.js           — перевірений список товарів (кошик)
    ua-order-service.js      — API-виклики (cart/add, departments, checkout/add), адаптовано з console-скрипта
    ua-oneclick-products.js  — товари для "1 клік" (за URL сторінки)
    ua-oneclick-service.js   — API-виклик one-click-order/, реверс-інжинирений з живого запиту
  pl/                      — (TODO) аналогічна структура для PL
```

`ua-config.js` завантажується двічі — і в popup (для рендеру чекбоксів), і в
вкладку сайту (для виконання) — це той самий файл, без дублювання логіки.

### Чому запити виконуються у вкладці, а не з popup

Popup — це `chrome-extension://` origin. Фетч звідти до сайту вважається
cross-site, тому SameSite cookies сесії не будуть передані. Тому реальні API-запити
виконуються через `chrome.scripting.executeScript` безпосередньо у контексті
відкритої вкладки — там `fetch(..., {credentials: 'same-origin'})` працює так само,
як і в оригінальному console-скрипті.

## Перевірка платформи / сайту

Два незалежні рівні перевірки:

1. **Site detection** (`core/site-config.js`, popup-only) — за hostname активної
   вкладки визначає платформу (`staging.exist.ua` → UA, `staging.exist.pl` → PL,
   плюс `exist.ua`/`www.exist.ua` тощо). Реальні домени можуть відрізнятись — весь
   mapping в одному місці, `SITE_HOSTNAMES` у цьому файлі, легко відредагувати.
   Якщо хостнейм не впізнано — `⚠️ Unknown site`, кнопка запуску заблокована.
   Якщо вибрана платформа не збігається з визначеною — `🔴 Невірна платформа`,
   запуск заблокований, поки не обрати правильну платформу або не перейти на
   відповідний сайт.
2. **Preflight-запит** `GET /api/v1/cart/?clear=0` у вкладці безпосередньо перед
   стартом — підтверджує, що сесія авторизована (401/403/помилка мережі → run
   не починається).

## UA — "Замовлення в 1 клік"

Окремий, спрощений флоу з кнопки на сторінці товару (тільки телефон, без вибору
доставки/оплати — менеджер потім передзвонює і уточнює деталі). Реверс-інжинирено
з живого запиту на staging:

```
POST /api/v1/orders/one-click-order/
```

Товаро-специфічні поля (`product_id`, `supprice_id`, `supprice_letter`, `dc_code`,
`price`, `delivery_time`) читаються напряму зі сторінки товару — вони вшиті в
`window.PRELOADED_STATE` (JSON у `<script>`), інших API-запитів для цього не існує.
Обліковий запис (`user`, `price_level`, `contract_agent`, `contract_object`,
`agreement_object`) береться звідти ж, з `PRELOADED_STATE.session`.

**Важливо:** сайт дозволяє **1 заявку "в 1 клік" на хвилину на телефон**
(`"Вы уже сделали заказ в один клик. Пожалуйста, подождите 1 минуту..."`). Runner
автоматично витримує паузу ~60с між такими заявками — тому кожна додаткова "1 клік"
заявка додає ~1 хвилину до загального часу прогону.

На відміну від кошика, товари для "1 клік" задаються в
`platforms/ua/ua-oneclick-products.js` через **URL сторінки товару**, а не числовий
id — бо `product_id` у цьому флоу не збігається з `product` із `cart/add/`. Список
наразі містить один перевірений товар; щоб додати ще — відкрийте сторінку товару,
переконайтесь що "Заказать в 1 клік" працює, скопіюйте шлях у список.

Успіх фіксується по HTTP-статусу; сайт не повертає номер замовлення синхронно
(заявка йде в чергу на підтвердження менеджером) — у результатах це показується
як "заявка прийнята" замість номера.

## UA delivery/payment коди

Коди перенесено 1:1 з оригінального console-скрипта (`platforms/ua/ua-config.js`):

**Доставка:** `office` (самовивіз), `nova_pochta`, `nova_pochta_postomat`,
`ukrpochta`, `exist_courier`, `exist_paid_courier`.

**Оплата:** `5` Готівка, `6` Наложний платіж, `175` Plata by mono, `177` Mono
розстрочка, `178` Privat розстрочка, `1` LiqPay, `72` Баланс, `2` Portmone.

Бізнес-правило: `exist_paid_courier` (платний кур'єр) не приймає готівкові способи
оплати (`5`, `6`) — така комбінація автоматично позначається `⚠️ Skipped`.

Товари, місто доставки (Київ) та ID магазину самовивозу — константи у
`ua-config.js` / `ua-products.js`, редагуються там за потреби.

### Mono/Privat розстрочка — чому потрібен другий запит

Для `payment` 177 (Mono) і 178 (Privat) сам `POST /api/v1/cart/checkout/add/` створює
замовлення, але кнопка **"Оплатити частями"** в історії замовлень з'являється лише
якщо після нього викликати ще й `GET /api/v1/cart/checkout/success/` (без параметрів,
без тіла) — саме цей запит реєструє заявку на розстрочку на стороні Mono/PrivatBank
і додає `additional_data.linked_entity` до замовлення. Це не додумано, а перевірено
наживо: ручний checkout на сайті теж робить цей запит одразу після відкриття
`/checkout/success/`, і без нього замовлення так само лишається без кнопки.

`ua-order-service.js` викликає цей другий запит автоматично для `payment` 177/178,
одразу після успішного `checkout/add`. Якщо він сам поверне помилку — замовлення
все одно рахується як `✅ Passed` (воно реально створене), просто в лозі буде
попередження, що кнопка могла не з'явитись.

## Генерація сценаріїв

Для обраних delivery × payment будується повна матриця комбінацій, кожна
позначається allowed/blocked через бізнес-правила платформи. Далі ця матриця
циклічно (round-robin, детерміновано) використовується, щоб отримати рівно
`N` (кількість замовлень) сценаріїв — незалежно від того, менше чи більше
валідних комбінацій було обрано. Товари з `ua-products.js` також підставляються
циклічно.

## Наступні кроки (не реалізовано в цій версії)

- **Phase 3 — PL**: `platforms/pl/pl-config.js`, `pl-products.js`,
  `pl-order-service.js` за аналогією з UA (пошук товару, категорія, checkout,
  random payment із доступних). Після появи адаптера додати відповідні файли в
  `injectEngine()` (`popup/popup.js`) і перевірити реальний PL-домен у
  `core/site-config.js`.
- Перевірити/доповнити реальні домени UA/PL у `core/site-config.js`
  (`SITE_HOSTNAMES`) — там зараз лише `staging.exist.ua`/`exist.ua` та аналоги
  для `.pl`.
